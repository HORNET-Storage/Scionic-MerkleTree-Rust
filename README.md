# Scionic Merkle Tree — Rust

A Rust implementation of the [Scionic Merkle Tree](https://github.com/HORNET-Storage/Scionic-Merkle-Tree)
— a chunked, verifiable-as-you-download Merkle DAG for directory trees and large
files.

A Scionic Merkle DAG combines the folder support of an IPFS-style Merkle DAG with
the small branch proofs of a classic Merkle tree. Each parent commits to its
children through a classic Merkle root, so a receiver can authenticate every leaf
as it arrives — independently, and without holding the whole structure.

## Status

Byte-compatible with the Go reference implementation at **v2.4.1**, across all five
layers of the parity specification.

| Layer | Scope |
|---|---|
| 1 — Primitives | CBOR, base32lower, base58btc, varint, CIDv1 |
| 2 — Classic Merkle tree | construction, proof generation, proof verification |
| 3 — Leaf hashing | CBOR → SHA-256 → CIDv1 → base32lower |
| 4 — DAG creation | filesystem walk, chunking, sequential and parallel |
| 5 — DAG operations | verify, serialize, transmit, diff, partial DAGs, store |

Compatibility is not asserted from a round trip against this crate's own encoder.
It is pinned against JSON and CBOR bytes generated by the Go implementation and
committed to this repository, so a divergence fails the test suite rather than
going unnoticed. [`PARITY.md`](PARITY.md) documents the wire contract and the
guards that hold it.

`#![forbid(unsafe_code)]`, a single dependency (`sha2`), no workspace, no FFI.

## Install

Not published to crates.io. Depend on it by git:

```toml
[dependencies]
scionic-merkletree = { git = "https://github.com/HORNET-Storage/Scionic-MerkleTree-Rust", tag = "v2.4.1" }
```

Requires Rust 1.85 or newer.

## Usage

### Build a DAG from a directory

```rust
use scionic_merkletree::create_dag;

let dag = create_dag("path/to/directory")?;
println!("root: {}", dag.root());
dag.verify()?;
```

Parallel creation builds a byte-identical DAG:

```rust
use scionic_merkletree::{create_dag_parallel, ParallelDagBuildOptions};

let dag = create_dag_parallel("path/to/directory", &ParallelDagBuildOptions::default())?;
```

Chunk size and other build settings live on `DagBuildOptions`, passed through
`create_dag_with_options`.

### Serialize

```rust
use scionic_merkletree::Dag;

let cbor = dag.to_cbor()?;
let restored = Dag::from_cbor(&cbor)?;

let json = dag.to_json()?;
let restored = Dag::from_json(&json)?;
```

### Transmit, verifying each leaf on arrival

```rust
use scionic_merkletree::TransmissionReceiver;

let mut receiver = TransmissionReceiver::new();
for packet in dag.get_leaf_sequence()? {
    receiver.apply_and_verify_transmission_packet(packet)?;
}
let received = receiver.into_dag()?;
```

Each packet carries the Merkle proof binding its leaf to the parent that packet
declares, so the receiver authenticates as it goes rather than trusting the sender
and checking at the end.

For larger transfers, `batched_leaf_sequence()` groups leaves into size-limited
packets:

```rust
use scionic_merkletree::BatchedDagReceiver;

let mut receiver = BatchedDagReceiver::new();
for batch in dag.batched_leaf_sequence()? {
    receiver.apply_and_verify(&batch)?;
}
let received = receiver.finish_verified()?;
```

### Partial DAGs

A partial DAG carries a subset of leaves plus the Merkle proofs needed to verify
them against the original root, so a peer can request specific files without
downloading — or being able to forge — the rest.

## Wire compatibility

The serialized envelope is byte-identical across Go, Swift and Rust. Two rules
make that true:

- **Struct fields ride in declaration order.** That is the shape deployed peers
  produce and expect.
- **The five genuinely dynamic maps are key-ordered** — `Leafs`,
  `AdditionalData`, `stored_proofs`, `proofs` and `Relationships` — sorted
  length-first, then bytewise over the UTF-8 key, which is RFC 8949's rule for
  text keys.

`stored_proofs` and `proofs` are omitted entirely when empty.

CID computation is a separate contract and none of the above touches it: the
hashed preimage flattens `AdditionalData` into a sorted array before hashing, so
no map iteration order can reach a CID.

## Performance

Measured against the Go reference on the same generated corpus at the same chunk
size. Both harnesses print their DAG root and the roots match
(`bafireifuqx7…lrqrmxi`, 141 leaves) — comparing timings between implementations
that built *different* DAGs would be meaningless, so the harness makes that
impossible to overlook. Both also report identical encoded sizes
(`cbor_bytes=19188357`, `json_bytes=25591601`).

18.25 MiB corpus, 256 KiB chunks, min of 7 samples, Windows / 24 CPUs / Go 1.24.4,
both harnesses run back to back in one session. Lower is better.

| Workload | Rust | Go | Rust vs Go |
|---|---:|---:|---|
| `verify` | 4.77 ms | 10.30 ms | **2.16× faster** |
| `from_json` | 50.46 ms | 68.51 ms | **1.36× faster** |
| `to_json` | 68.22 ms | 83.82 ms | **1.23× faster** |
| `to_cbor` | 4.29 ms | 5.06 ms | **1.18× faster** |
| `create_parallel` | 3.89 ms | 4.53 ms | **1.17× faster** |
| `leaf_sequence` | 2.52 ms | 2.74 ms | **1.08× faster** |
| `from_cbor` | 2.60 ms | 2.49 ms | parity (1.04×) |
| `create_sequential` | 18.31 ms | 16.26 ms | 1.13× slower |
| `batched_sequence` | 0.114 ms | 0.089 ms | 1.29× slower |

Leaf payloads are shared through `Arc` rather than deep-copied, so cloning a leaf
— which transmission, batching and every store read do constantly — is a refcount
bump. This is sound because leaf content is immutable: a leaf's CID commits to
`sha256(content)`, and `Arc` hands out no `&mut` while a second owner exists, so
the invariant is enforced by the type system rather than by convention.

Two workloads remain slower. `create_sequential` is 1.13×, consistent with the
overflow-checked arithmetic and allocation-failure handling this crate performs;
note that `create_parallel`, the path most callers use, is 1.17× *faster* and
builds an identical DAG. `batched_sequence` is 1.29× on a workload whose absolute
cost is 114 µs.

Run-to-run variance is roughly ±5%, and the machine drifts about that much
*between* sessions, so only same-session ratios are meaningful — comparing a Rust
number taken today against a Go number recorded last week will invent a regression
that is not there. Both harnesses calibrate an inner repetition count until each
timed region spans at least 100 ms, then divide; without that, the fast workloads
measure the clock rather than the code.

## Versioning

Ports mirror the Go library's version number. A port's version is a claim about
*which Go release it reproduces byte for byte*, not an independent release
history — a port never bumps on its own, it bumps when it catches up to a Go
release.

This crate reached parity at Go `v2.4.1`, so `v2.4.1` is its first tag. Port-only
fixes append a suffix (`v2.4.1+rust.1`) rather than moving the base version, so
the base always means exactly one thing.

## Development

```bash
cargo test
cargo clippy --all-targets -- -D warnings
```

114 tests cover layers 1–5, the committed Go wire vectors, and the shared
spec-vector corpus under `spec/vectors`.

`tools/gobench` and `tools/gowirevectors` are Go programs that regenerate the
comparison vectors and benchmark against the reference. They resolve the Go
library through a local `replace` directive and expect a checkout of
[Scionic-Merkle-Tree](https://github.com/HORNET-Storage/Scionic-Merkle-Tree)
alongside this repository. Neither is needed to build or test the crate.
